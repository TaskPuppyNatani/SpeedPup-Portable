# Phase 4C — Connection Intelligence

Intelligence is a deterministic, local interpretation of stored run summaries. It performs no network requests, telemetry, LLM calls, automated configuration, or overall health scoring. Observations distinguish sufficient measured patterns from informational coverage gaps; recommendations are investigation steps, not diagnoses or guaranteed remedies.

## Architecture and evidence

`core.intelligence` defines Qt-independent `Fact`, `Observation`, `Severity`, and `IntelligenceResult` contracts. An observation has a stable rule ID and category, title, severity, sufficiency flag, explanation, independent run and matching counts, UTC observation period, relevant statistics, conditions, next steps, and limitations. Recommendations are deduplicated in deterministic observation order. An identical record ID cannot count twice; conflicting duplicates are excluded. The engine sorts facts and observations deterministically.

Intelligence evaluates at most **512 matching run summaries**. It reserves up to 256 each for Speed Tests and Diagnostics, and redistributes unused slots to the category with more matching runs. Diagnostics slots are split as evenly as possible among Quick, Standard, and Full, with surplus slots redistributed among profiles that still have rows. Quick, Standard, then Full breaks ties when assigning remainder slots. Each population keeps its newest matching records in descending completion-time and record-ID order.

SQLite counts and selects within one read transaction and after applying the active time, interface, and measurement-category filters. It uses up to four bounded scalar queries and does not use chart points or hydrate samples for evidence selection. The pure analysis and report paths use the same allocation policy. Analysis, the Speed Test sidebar, and reports show total and evaluated populations, including diagnostic profile counts. Supporting observations distinguish measured values, eligible evidence, and the largest comparable group. When omitted evidence could affect an insufficiency conclusion, the coverage text points to a narrower scope and does not recommend collecting more solely because of the cap. Descriptive statistics and charts retain their own populations.

The generic repository fallback is intended for mocks and tests. It accumulates all matching records in memory and requests no samples, but a repository may still hydrate child details. The fallback does not claim database-wide interface enumeration without a `list_interfaces()` capability. SQLite is the production implementation. SQLite reports for explicit record selections or text-search scopes retain their existing scoped-record analysis inside the export snapshot rather than using the normal scalar Analysis retrieval path.

Comparable Speed Tests require the same recorded interface, server ID and host, application version, and HTTP Speed Test method. Diagnostic comparisons require the same interface, profile, target setting, application version, and ICMP method; DNS also requires the same recorded resolver. Full load comparisons additionally require the same budget, recorded saturation status, and presence or absence of a worker-related qualification. Runs missing interface, version, or required server information do not form comparison groups. An automatic target is grouped with automatic target within an application version; resolver or network configuration can still change under the same displayed identity. The same interface does not establish that two runs used the same network or internet connection.

Unavailable metrics are not zeros. Zero ICMP loss is a valid result for those attempts, not proof of overall connection health. Grades are never numerically averaged. Full load rules require an available stored grade, a recorded qualification note, a baseline, and the applicable direction's loaded latency and increase. Download and upload coverage separately require three eligible runs in a comparable group. A supported finding in one direction can coexist with limited evidence in the other. The stored grade is treated as the original run's eligibility decision; probe-level coverage is not rechecked by this summary query. Worker-related notes are retained in observations and grouped separately; exceptionally long notes are excerpted with a pointer to History. Estimated saturation status is preserved as recorded and is not independently verified. Descriptive load-increase statistics include measured values from ungraded Full runs and disclose their directional counts. A measured increase alone does not establish sustained load or saturation.

## Rule reference

All numerical thresholds below are **SpeedPup heuristics**, not claims of an external standard. A run, not an individual probe, is the unit of evidence. Repeated rules require at least three valid comparable runs and at least two triggering runs. Earlier/later comparisons additionally require a span of at least one day, split at its midpoint, with at least three valid runs on each side and two later runs meeting the trigger. Median calculations use all relevant runs in the bounded evidence window.

| Rule ID | Required evidence | Trigger and observation | Qualifications / suggested action |
| --- | --- | --- | --- |
| `throughput_{download,upload}.recent_low` | ≥6 comparable Speed Tests | ≥2 of last 3 ≤70% of the median of preceding runs; repeated low throughput | No subscribed speed is assumed. Repeat with same server and controlled traffic; compare wired/Wi-Fi where practical. |
| `throughput_{download,upload}.period_change` | ≥3 runs in each distinct period | Later median ≤70% of earlier median and ≥2 later runs meet that level | Observed change, cause unknown; repeat with the same server and interface. |
| `throughput_{download,upload}.variability` | ≥5 comparable runs | ≥2 at or below 60% and ≥2 at or above 140% of median | An isolated outlier is insufficient; check concurrent traffic and repeat. |
| `icmp_latency.repeated_elevated` | ≥3 valid comparable diagnostics | ≥2 baseline ICMP means ≥100 ms | Target-specific, not every application; repeat and investigate ICMP filtering. |
| `jitter.repeated_elevated` | ≥3 valid comparable diagnostics | ≥2 jitter values ≥15 ms | Adjacent-reply ICMP variation; repeat and compare application behavior. |
| `{icmp_latency,jitter,dns_latency}.period_change` | ≥3 valid comparable runs in each distinct period | Later median and ≥2 later runs ≥150% of earlier median and at least 20/10/50 ms higher respectively | Causes are unknown; repeat the relevant check under comparable conditions. |
| `packet_loss.isolated` | ≥1 available loss result | One observed nonzero loss without enough evidence for recurrence | Informational; ICMP filtering or deprioritization may contribute. Repeat diagnostics. |
| `packet_loss.repeated` | ≥3 available comparable results | ≥2 nonzero-loss runs | Warning, not proof of total internet packet loss; repeat and investigate filtering. |
| `packet_loss.measured_zero` | ≥1 available loss result | All comparable available results are zero | Describes only these attempts and does not establish health. |
| `dns.repeated_failures` | ≥3 available comparable DNS failure counts | ≥2 runs with at least one failed lookup | DNS failures do not prove the cause of other problems; investigate resolver configuration and caching. |
| `dns_latency.repeated_elevated` | ≥3 valid comparable DNS timing results | ≥2 median lookups ≥100 ms | Successful-lookup timing is separate from failures; cache and resolver can change. |
| `bufferbloat_{download,upload}.repeated_elevated` | ≥3 comparable eligible Full results for that direction | ≥2 added-latency values ≥30 ms | Estimated load, not confirmed saturation or router/ISP fault; investigate concurrent traffic and QoS/SQM capabilities. |
| `coverage.*` | Any scope, including empty | Missing measurements, too few comparable runs, mixed conditions, short periods, or truncated evidence window | Informational only; collect more comparable runs where appropriate. |

## Presentation, lifecycle, and failure handling

Analysis computes intelligence on its existing asynchronous reader and renders it alongside the same snapshot's charts, statistics, and coverage. New filter requests clear prior intelligence during loading, and the existing latest-request guard discards stale results. The display limits the number of rendered observations and points to the omitted count. A rule-engine exception produces an explicit unavailable-intelligence observation while leaving computed descriptive statistics intact; storage/query errors use the existing nonfatal Analysis error state.

The Speed Test sidebar uses a separate asynchronous Analysis reader with an **all saved history** scope, independent of the Analysis page's filters. It labels the most recent session test separately from historical observations and limits historical rendering. After persistence succeeds it refreshes after pending writes drain. History failure does not change a successful current Speed Test. Both readers are invalidated and drained during shutdown; no periodic polling or automatic measurement is introduced.

## Native acceptance and limits

Use an isolated test history or known saved runs. Check empty and one-run states, mixed interfaces/servers/profiles, measured zero versus unavailable loss, repeated runs, and Full runs with differing budgets and worker qualifications. Exercise time/interface/category filters, rapid filter changes, persistence refresh, failed storage, narrow-window scrolling, and shutdown during reads. On the Speed Test page verify current results and all-history scope remain distinct and that neither page starts network tests. Interactive Linux, Windows, and macOS acceptance remains the user's task.

The 512-run cap can omit older comparable groups within a category or profile. Allocation does not reserve individual slots for each interface, server, target, resolver, or load condition. Measurement populations are still imperfect proxies for a connection: interfaces, resolvers, servers, caches, and background traffic can change without being captured. These rules cannot identify the ISP, router, or other cause and cannot establish that no problem exists. Independent durability, migration, privacy, and analytical correctness review remains required before sealing.
